# 开发计划与路线图

> 最近更新：2026-08-29
> 原则：优先增强核心闭环和可验证性；模型生图是唯一计划中的生成图像路线。

## 1. 路线图目标

在保持纯本地角色库、MCP 风格本地接口、多模型、TTS 和自定义角色能力的前提下，将当前原型演进为：

1. 情绪理解会真实改变玩家后续获得的信息和操作难度。
2. 调酒是叙事回应，而不只是三维数值匹配。
3. 顾客会记住玩家，并在后续访问中证明之前的行为产生过影响。
4. 核心规则具有自动测试，存档变化具有明确契约。
5. 视觉增强与业务规则分离，避免渲染技术反向绑架玩法。

## 2. P0：规则可靠性与文档收口

### 2.1 建立测试基线

任务：

- 引入 Vitest 和基础测试环境。
- 为纯函数建立首批测试。
- 在 `package.json` 增加稳定的 `npm test` 命令。

优先测试：

- 三维混合值计算。
- 杯型容量与份量增减。
- 条件判断、容差和目标可解性。
- 三情绪组合目标。
- h=0–3 命中奖励和表面情绪额外信任。
- 十字路口确定性解析。
- 存档合并和旧字段迁移。

验收：

- 核心纯规则在无浏览器和无真实模型的环境下可重复运行。
- 同一输入得到稳定结果。
- `npm test` 与 `npm run build` 均通过。

### 2.2 拆分调酒纯规则

将 `src/utils/cocktailMixing.js` 逐步拆分为：

```text
src/utils/mixing/
├─ constants.js
├─ effects.js
├─ conditions.js
├─ solver.js
├─ portionOps.js
├─ suggestions.js
└─ index.js
```

先保留原文件作为兼容出口，避免一次性修改所有调用方。

### 2.3 建立版本化存档契约

在 `shared/` 中集中维护：

- 存档 schema 版本。
- 默认游戏状态。
- NPC profile 与 memory 结构。
- 旧字段过滤与迁移规则。
- 前后端共享的规范化函数。

验收：旧存档可以加载，新字段缺失时有明确默认值，迁移失败不会静默破坏数据。

## 3. P1：增强核心玩法

### 3.1 情绪判断 A/B/C/D 评级

在现有命中数逻辑上增加统一结果：

```js
{
  grade,
  coreEmotion,
  matchedEmotions,
  summary,
  benefits: {
    trustBonus,
    guidanceLevel,
    tolerancePercent,
    revealTargetConditions
  }
}
```

评级不阻断游戏，而是影响：

- 是否公开精确目标。
- 提示完整度。
- 预览容差。
- 信任与反馈。

### 3.2 鸡尾酒叙事意图

在情绪与三维条件之间增加语义层：

```text
顾客状态
  → 应该表达的态度
  → 安抚/试探/鼓励/保持距离等叙事意图
  → 三维方向
  → 当前材料可解的具体目标
```

验收：玩家能从提示理解“这杯酒想表达什么”，系统仍能证明目标在当前解锁材料下可解。

### 3.3 关系回声最小闭环

在现有回头客数据中增加：

```js
{
  immediateEcho,
  returnPlan,
  proofDebt
}
```

目标：重要玩家行为在有限天数内至少产生一次可见后果，不完全依赖随机回访。

### 3.4 AI 角色口吻剩余工作

已完成 Prompt 锚点和防复读，下一步：

- 将普通对话温度从固定 `0.75` 调整为可配置，并做 0.65–0.75 对比测试。
- 增加禁用词、签名意象和重复 n-gram 的本地评分。
- 评分过低时最多重写一次。
- 为回头客建立“必须引用一条具体共同记忆”的验证。
- 保存多轮人工评测记录，而不是只写目标值。

### 3.5 默认角色内容对齐

Captain Quick 与 Aquabyte-98 已共同进入默认角色池，但 Aquabyte-98 的文本清单仍需补齐：

- 明确 `categoryId`，避免按内部 ID 哈希回退分类。
- 编写专属 `dialogueStyle.tone`、features 和 opening lines。
- 将通用 voice opening lines 替换为符合“数字海洋、怀旧、守护微型生态”设定的表达。
- 明确代词或无性别表达策略，并更新 gender 元数据。
- 建立两名默认角色的字段完整度清单，避免“可以加载”被误认为“内容同等完善”。

验收：两名默认角色具有同级别的角色专属对话信息，并完成至少一轮人工多轮口吻对比。

## 4. P2：自动游玩与可观测性

### 4.1 可见状态协议

为自动玩家公开：

- 当前页面和游戏阶段。
- 玩家当前能看到的顾客、对话与提示。
- 当前可执行动作。
- 可交互目标及其稳定 ID。
- 阻塞覆盖层和等待状态。

自动测试不得直接修改内部 React 状态来绕过玩家路径。

### 4.2 端到端测试

覆盖：

- 新游戏与角色配置。
- 顾客加载失败后的恢复。
- 对话、情绪选择、调酒、递酒与日结。
- 存档重载。
- 模型不可用时的可读错误。
- 模型生图失败时不阻断核心玩法。

### 4.3 自定义角色选择界面

当前 New Game 只保留 `Add a Custom Character` 开关，勾选后不展示候选列表。后续在产品交互确定后补充：

- 本地自定义角色列表与空状态。
- 单选角色的名称和缩略图展示。
- 不暴露内部 ID。
- 取消选择后恢复 Captain Quick 与 Aquabyte-98 默认随机池。

## 5. P3：表现层增强

### 5.1 模型生图管线增强

统一路线：

```text
角色 profile/提示词
  → 服务端模型生图请求
  → 响应校验
  → 透明背景或裁切处理
  → 角色目录缓存
  → 游戏运行时读取
```

计划补充：

- 提供商超时、限流和错误映射。
- 失败重试上限。
- sourceHash/模型/提示词版本记录。
- 生成图替换、清理和回滚操作。
- 版权、来源和演示用途标记。

### 5.2 选择性接入 Pixi

推荐顺序：

1. 先接入氛围背景、光影与粒子。
2. 增加酒液、杯体和递酒动画。
3. 保留 React/DOM 的文本、卡片和可访问按钮。
4. 只有在确认展示收益后，才评估将调酒核心操作区迁入 Canvas。

具体范围需要先完成 [待商讨与决策.md](待商讨与决策.md) 中的渲染决策。

## 6. 暂不进入开发承诺

以下内容在形成决策前不排入实现：

- 是否恢复章节主线。
- 是否恢复事件、图鉴或商店。
- 是否引入独立叙事服务。
- 每日顾客数量的最终产品规则。
- 调酒台是否全面 Canvas 化。

## 7. 计划维护方式

- 每个任务必须包含“玩家价值、涉及范围、验收标准”。
- 完成后将事实写入 `当前状态与已完成.md`，并从本文删除或移入“已完成”。
- 被放弃的路线直接删除，不在当前计划中保留“也许以后”。
- 外部研究只放入 `research/`，不能自动成为开发承诺。
