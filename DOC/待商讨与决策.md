# 待商讨与决策

> 最近更新：2026-08-28  
> 本文只记录需要产品、设计或架构选择的事项，不代表已经排期。

## 1. PixiJS 接入范围

### 当前事实

- 项目依赖 PixiJS，仓库内也有 Pixi 场景实现。
- 当前调酒台和氛围层的主要运行路径仍是 React/DOM。

### 需要决定

选择其一：

1. **混合渲染，推荐**：DOM 负责文字、按钮和卡片；Pixi 负责背景、光影、粒子、酒液与动画。
2. **调酒区 Pixi 化**：将调酒卡片和操作区迁入 Canvas，保留外围 DOM。
3. **全面 Pixi 化**：只适合明确追求游戏画面统一、且愿意承担无障碍与手工布局成本的情况。

### 决策依据

- 课程或展示是否明确要求 Pixi 交互。
- 手机端和小窗口适配需求。
- 键盘、屏幕阅读器和自动测试要求。
- 是否有足够时间维护 Canvas 滚动、命中区域和文本排版。

## 2. 主线章节是否恢复

### 当前事实

- `useChapterSystem.js` 仍存在。
- `STORYLINE_ENABLED = false`，正常日结不会推进主线章节。
- 调酒模式与章节配置仍有关联，因此默认流程可能长期停留在 strict。

### 需要决定

- 保持“无主线、专注单客体验”。
- 恢复完整章节与结局。
- 只恢复调酒模式成长，不恢复主线剧情。

推荐优先讨论第三种：把玩法教学和模式成长从主线剧情中解耦。

## 3. 回头客与独立叙事服务

### 当前事实

- 前端已有回头客池、角色弧光、共同历史和十字路口。
- Node 存档服务已有 NPC profile 和 session memory。

### 需要决定

- 继续在现有 React + Node 架构中增强长期记忆。
- 引入独立叙事服务，负责 NPC memory、teaser 和会话总结。

推荐先完成关系回声和版本化存档契约；只有当多轮长期记忆成为核心展示目标时，再讨论增加额外服务。

## 4. 每日顾客数量规则

### 当前事实

当前每日上限等于启用角色数量，最少为 1；这与历史文档中的“固定 3 位”不同。

### 候选方案

1. 固定 3 位，节奏稳定。
2. 等于启用角色数，适合严格角色验证。
3. `min(启用角色数, 配置上限)`，兼顾验证和正式玩法。

推荐第三种，并将上限做成显式配置，不再隐藏在 Hook 内。

## 5. 三情绪组合权重

### 当前事实

strict/transitional 使用三个所选情绪的等权平均向量。

### 需要决定

- 保持等权，规则容易理解。
- 第一个选择视为主情绪，使用主情绪加权。
- 根据情绪判断评级或对话证据动态分配权重。

推荐先保留等权作为稳定基线，待 A/B/C/D 判断系统完成后再测试主情绪加权。

## 6. 模型生图策略

### 已确定

- 后续角色图片统一使用模型生图 API。
- 生图失败不能阻断对话、情绪判断和调酒核心流程。
- 生成结果必须进入统一的角色资产目录和缓存管理。

### 仍需决定

- 默认模型和备用模型。
- 国内/香港网络下的备用兼容端点。
- 生成图是否默认自动替换旧图，还是需要人工确认。
- 是否保留原图、提示词、模型版本和 sourceHash。
- 角色肖像、立绘和 cutout 是否使用一次生成还是分阶段生成。
- 生成素材的版权披露和演示使用规则。

推荐：生成后先进入候选状态，人工确认后再替换运行时资产。

## 7. 停用系统的去留

需要逐项决定“永久删除、继续停用、重新设计”：

- 随机事件与奖励事件。
- 图鉴。
- 商店。
- 今晚影响数值修正。
- 旧教程覆盖层。

决定前不建议继续为这些系统增加新功能。
